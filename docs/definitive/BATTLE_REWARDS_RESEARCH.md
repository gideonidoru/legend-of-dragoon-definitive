# Battle Rewards Mod — reuse assessment

Inspected 2026-10-09 against official baseline `fba1543543865e29ee572f479003d9b47158eeb3`, Java 25. Recommendation: retain the small **optional XP/gold settings concept**, implemented as a separate current-API mod if selected. Do not install, bundle or claim compatibility for the published 1.5.0 ZIP from this research. The repository source does not build unchanged against our baseline, and source-to-release correspondence is unproven.

## Exact behavior and upstream overlap

The [reward handler](https://github.com/DennytXVII/BattleRewardsMod/blob/7f7ed8c450ac3945784fd7bde8a58834910e6f6c/src/main/java/examplemod/EnemyRewardModifier.java#L39-L44) independently performs `Math.round(multiplier * event.gold)` and `Math.round(multiplier * event.xp)`. It registers with the normal event/config registries; it does not patch engine classes. The ID remains **`enemy-reward-modifier`**, with **`gold_modifier`** and **`xp_modifier`** configuration keys, despite the newer project/file naming.

| Aspect | Source-verified behavior |
| --- | --- |
| Reward timing | Engine [Battle.loadEnemyDropsAndScript](https://github.com/Legend-of-Dragoon-Modding/Severed-Chains/blob/fba1543543865e29ee572f479003d9b47158eeb3/src/main/java/legend/game/combat/Battle.java#L9302-L9316) posts EnemyRewardsEvent when each enemy's rewards are loaded, then stores the modified values on that combatant. Scaling occurs per enemy, before death reward accumulation and party distribution. |
| Rounding | Positive half values round upward. Derived example: three enemies worth 1 XP each at 0.5x produce `1 + 1 + 1 = 3` XP, rather than rounding the combined 1.5 XP to 2. At 0x, the handler produces zero XP/gold for ordinary nonnegative rewards. These are arithmetic/source deductions, not gameplay observations. |
| Item drops | No calls to EnemyRewardsEvent.clear/add and no change to drop chances, items, quantities or the random roll. The [engine death/drop path](https://github.com/Legend-of-Dragoon-Modding/Severed-Chains/blob/fba1543543865e29ee572f479003d9b47158eeb3/src/main/java/legend/game/combat/Battle.java#L4296-L4328) retains its existing drop logic. This is not a drop-rate mod. |
| Character XP | The engine [PostBattleScreen](https://github.com/Legend-of-Dragoon-Modding/Severed-Chains/blob/fba1543543865e29ee572f479003d9b47158eeb3/src/main/java/legend/game/inventory/screens/PostBattleScreen.java#L141-L162) divides total XP among living active characters, then computes reserve XP using its own multiplier. A reward multiplier changes that total before distribution; it does not redefine the recipients or divisor. |
| Existing XP option | Upstream [SecondaryCharacterXpMultiplierConfigEntry](https://github.com/Legend-of-Dragoon-Modding/Severed-Chains/blob/fba1543543865e29ee572f479003d9b47158eeb3/src/main/java/legend/game/modding/coremod/config/SecondaryCharacterXpMultiplierConfigEntry.java) controls reserve-character XP from 0–100%, default 100%; the [Vanilla preset](https://github.com/Legend-of-Dragoon-Modding/Severed-Chains/blob/fba1543543865e29ee572f479003d9b47158eeb3/src/main/java/legend/game/saves/ConfigPresetManager.java#L210-L225) uses 50%. This overlaps progression control but is not a global enemy-XP multiplier. Reserve XP compounds the two settings, with engine truncation. |
| Other progression | Main/tagged handler does not change Addition mastery, SP or Dragoon XP, scripted/non-enemy rewards, encounter rate, level requirements or item prices. Scaling affects existing level-up and gold systems downstream. It adds no reward-total overflow/saturation guard; existing engine limits are not evidence for arbitrary other-mod inputs. |

The inspected baseline has the **EnemyRewardsEvent seam and configurable reserve XP**, but no equivalent built-in global enemy XP/gold multiplier found in its registered configuration/source. Prefer this seam over importing old progression internals. Other handlers can also modify the same mutable [event](https://github.com/Legend-of-Dragoon-Modding/Severed-Chains/blob/fba1543543865e29ee572f479003d9b47158eeb3/src/main/java/legend/game/modding/events/battle/EnemyRewardsEvent.java). Composition/order is an integration concern: sequential scaling and rounding can differ from one combined multiplier. The mod establishes no ordering/exclusivity policy.

## Configuration, saves and faithful mode

Both [tagged XP configuration](https://github.com/DennytXVII/BattleRewardsMod/blob/da1a97acd95d7a346205a89c3b0c002213e10596/src/main/java/examplemod/XPModifierConfigEntry.java) and the older main `examplemod` configurations use **1.0x defaults**, **0.25x increments**, and **0.25–10.0x** UI bounds. Main's added [XP](https://github.com/DennytXVII/BattleRewardsMod/blob/7f7ed8c450ac3945784fd7bde8a58834910e6f6c/src/main/java/battlerewardmod/XPModifierConfigEntry.java) and [gold](https://github.com/DennytXVII/BattleRewardsMod/blob/7f7ed8c450ac3945784fd7bde8a58834910e6f6c/src/main/java/battlerewardmod/GoldModifierConfigEntry.java) files instead allow **0–10.0x**; this agrees with the intent of [v1.3.0's zero-reward notes](https://github.com/DennytXVII/BattleRewardsMod/releases/tag/v1.3.0), but does not establish the ZIP's implementation. Report the two source sets separately.

Persistence is **CAMPAIGN**, not per save slot or global. Serialization stores `round(value * 4)` in one byte; decoding reads an unsigned byte divided by four. A non-one-byte value falls back to **0.25x**, not the 1.0x default. There is no deserializer range validation: one-byte inputs can encode **0–63.75x**, beyond the advertised UI range. Both UI bounds and byte validation should be explicit in any adaptation.

The engine [Campaign](https://github.com/Legend-of-Dragoon-Modding/Severed-Chains/blob/fba1543543865e29ee572f479003d9b47158eeb3/src/main/java/legend/game/saves/Campaign.java) uses `campaign_config.dcnf`, while [ConfigStorage](https://github.com/Legend-of-Dragoon-Modding/Severed-Chains/blob/fba1543543865e29ee572f479003d9b47158eeb3/src/main/java/legend/game/saves/ConfigStorage.java#L79-L142) skips unknown registry IDs on load and serializes registered entries on save. Inference: saving campaign configuration without the mod may drop its unregistered settings; reinstall cannot promise to recover them. [Campaign selection](https://github.com/Legend-of-Dragoon-Modding/Severed-Chains/blob/fba1543543865e29ee572f479003d9b47158eeb3/src/main/java/legend/game/inventory/screens/CampaignSelectionScreen.java#L129-L151) also tracks enabled/missing mods and may require user confirmation. This is not proof of safe uninstall or save round trips.

No custom save schema or migration is supplied by this mod. Nevertheless, awarded XP, resulting levels and spent/retained gold become ordinary persisted progression. Returning both settings to 1x or removing the mod cannot undo that history. Back up the **whole campaign including its configuration**, and use a separate campaign for altered progression. Faithful mode must explicitly ensure **1x XP, 1x gold**, alongside the upstream Vanilla reserve-XP rule; selecting a preset is not retrospective restoration. Since rewards are captured on enemy loading, changing settings during battle need not update already loaded enemies; summoned/reloaded enemies may see newer values. That timing inference needs a defined policy and runtime tests.

## Build/API compatibility evidence

The pinned [build.gradle.kts](https://github.com/DennytXVII/BattleRewardsMod/blob/7f7ed8c450ac3945784fd7bde8a58834910e6f6c/build.gradle.kts) targets **Java 17**, version **1.0-SNAPSHOT**, and an unpinned local **`legend:lod:snapshot`** dependency. It has legacy JavaFX/LWJGL/shadow setup and a Gradle 8.0 wrapper, rather than an engine-SHA lock or a release-specific build recipe. Our [baseline build](https://github.com/Legend-of-Dragoon-Modding/Severed-Chains/blob/fba1543543865e29ee572f479003d9b47158eeb3/build.gradle#L20-L22) targets Java 25. Java 17 alone is not the rejection reason; the actual source/API failures are.

A headless **javac 25** probe attempted to compile all six pinned main Java files unchanged with annotation processing disabled, against our locally built baseline engine/dependency JARs. It exited **1 with 15 diagnostics**, not a successful compilation. No engine class was initialized or game launched. Reproduction command, with source retrieved only as text under temporary storage:

```sh
/private/tmp/lod-definitive-tooling/amazon-corretto-25.jdk/Contents/Home/bin/javac \
  -proc:none \
  -cp '/Users/markmurray/Downloads/Development/legend-of-dragoon-definitive/build/libs/lod-game-snapshot.jar:/Users/markmurray/Downloads/Development/legend-of-dragoon-definitive/build/libs/libs/*' \
  -d /private/tmp/lod-battle-rewards-research/classes \
  /private/tmp/lod-battle-rewards-research/main/battlerewardmod/*.java \
  /private/tmp/lod-battle-rewards-research/main/examplemod/*.java
```

Failures: `BattleRewardModifier.java` declares public `EnemyRewardModifier`; three duplicate `examplemod` classes; unavailable imports `CharacterStatsEvent`, old `legend.game.types.CharacterData2c` and `LevelStuff08`; `@Mod` lacks the loader's required `version`; both added configurations use the obsolete four-argument constructor instead of the baseline [ConfigEntry constructor requiring ConfigCategory](https://github.com/Legend-of-Dragoon-Modding/Severed-Chains/blob/fba1543543865e29ee572f479003d9b47158eeb3/src/main/java/legend/game/saves/ConfigEntry.java#L21-L27). The relevant local ConfigEntry/EnemyRewardsEvent sources had no difference from the fixed baseline. This probe rejects unchanged main source; it does **not** prove that the separately uploaded 1.5.0 binary shares those failures.

1. Keep this lower priority than controller usability, install/update/save reliability and visual integration. It is an optional progression modifier, not a faithful-remaster prerequisite.
