# Repair, Reinstall and Uninstall recovery

The current public Steam Deck installer could report “Cannot resolve an interrupted game launch safely” after normal quit. A stale launch receipt made recovery enumerate every process; unrelated live processes with unavailable identity/argv were treated as potential game children. The regression reproduces that exact message before the fix.

Repair, Reinstall and Uninstall now stop this installation's verified game/launcher/workers before acquiring maintenance ownership. Process termination requires the same OS user and Java executable, effective installation-root/token JVM properties, and a recognized managed game entry or valid recorded launch token. Launchers require the actual manager entry or this root's manager JAR followed by exactly `--play ROOT`. Advisory receipts do not authorize terminating an unrelated recorded PID. Corrupt or missing receipts do not prevent identifying the actual managed entry. JVM option operands and trailing application arguments do not assign ownership; repeated or bare properties follow Java's last-assignment semantics. Descendant identities are captured while ownership is verified. Every signal rechecks process start time to avoid PID reuse. TERM has a bounded grace period, then remaining owned processes receive KILL. Missing or ambiguous ownership never authorizes terminating another application. Ordinary Update, Restore and unrelated installation operations retain their existing concurrency protection.

The `/proc` fallback excludes the executable, matching Java's normal argument-array contract. Linux's Java process API can omit argument vectors longer than one page. A bounded read of NUL-separated `/proc/PID/cmdline` supplies exact argv for those children. Flattened command text never authorizes termination: spaces, prefix paths and marker text inside another argument must not identify another installation as ours.

The exclusive operation lock and OS game lease remain held throughout maintenance, including download, verification and activation. Pending tokens are revoked while the lease is held; the new game entry validates its token only after taking its lifetime game lease. A rejected child leaves parent-owned receipts alone. The launcher cleans receipts while holding operation ownership, and subsequent maintenance reclaims stale receipts. Busy handoffs are retried for a bounded interval without re-running any maintenance work. Play releases only its temporary idle game lease before spawn, retaining its operation ownership; the actual game JVM then owns its own lifetime lease.

Maintenance revokes malformed and stale lifecycle records under both OS leases. Installation discovery stays read-only and preserves the recorded custom folder even with damaged state. Explicit maintenance defers transaction recovery until the game has stopped. Opening Manage can route a verified manager and closed dependency inventory through a partial bootstrap publication without stopping any game; actions recover the complete bootstrap pair under ownership. Missing-state and recovered-state screens retain access to all maintenance actions.

Same-release Repair retains saves, settings, module choices, imported discs and the active prepared workspace. Reinstall retains personal data/choices and retrieves the complete package with fresh preparation generations. Uninstall removes managed application/workspace files, retains personal data and imported discs, and removes discs only when the user selects that option. The progress phase identifies when the managed game is being closed. If the installed hosted release has been retired (HTTP 404), Repair uses the verified current release and fetches only changed/missing files; permission/network failures do not trigger a version change, and known installed publication dates prevent downgrades. This retired-release repair activates a newer version/data workspace using ordinary update semantics; the previous prepared workspace remains retained, and the installer returns to disc/preparation setup when the new workspace needs preparation.

## Verification

- The exact opaque-process classifier regression fails with the user's error on the old guard and passes after the change.
- A real headless process exits normally leaving both durable launch receipts; maintenance clears them automatically and preserves personal data.
- The actual installed root router starts a headless fixture game; explicit maintenance stops its game/manager workers, keeps an unrelated process alive, and preserves data/workspace.
- Uninstall reproduces refusal on the previous operation-only path; actual game and returned-worker cases now stop before application deletion and preserve saves/ISOs and unrelated processes.
- Missing/corrupt receipts, a live unrelated PID, missing state, partial bootstrap transactions and nondefault installation discovery are covered. Linux long-argv tests exercise both actual root launcher and actual ManagedGameMain with unusable receipts.
- Retired-release Repair uses a real selective-delivery fixture; HTTP 403 and known-date downgrade fixtures retain the installed version.
- Both leases are retained during maintenance and released after an injected failure.
- Exact-root/token cases include paths with spaces, sibling/prefix roots and markers embedded in unrelated arguments.
- A captured published `5c0783297` game-entry source is compiled with one gate immediately after its old pre-lease token validation. Repair terminates that real paused legacy process before maintenance. Its 16K command exercises Linux's exact `/proc` argv fallback in hosted Linux tests.
- Existing interrupted parent/child, native lifetime lease, returned non-daemon worker, PID reuse, damaged-state, symlink and transaction-recovery checks remain required.

These are source and headless OS-process checks. Physical Steam Deck exit/Steam Stop/suspend behavior remains device acceptance. A legacy child whose owner/argv cannot be read at all cannot be safely terminated; the retained lease protects maintenance writes. New entries enforce revocation after acquiring the lease. This is not a claim of proven behavior for every opaque older binary or sandbox.
