# Loader failures and MRG aliases

The source audit reproduced three loader defects: cyclic MRG aliases trapped a worker; a missing physical root silently shortened the returned list; asynchronous read failures were logged and converted to successful `null` results. Additional controlled executor tests found that rejected submissions and cancellation of the returned consumer future could leave the loading counter elevated.

MRG loading now validates unique nonnegative contiguous entry indices and nonnegative sizes, builds the result by index, loads each physical root once, and resolves aliases iteratively with cycle detection and memoized roots. Unknown targets, aliases of explicitly absent entries and missing physical roots fail with directory context. Declared absent entries retain null slots. Real empty files and directory placeholders retain their previous meaning, including directory aliases. Virtual files preserve root bytes, physical length, root index and per-entry virtual-size metadata. Normal non-MRG ordering and empty-directory behavior are unchanged.

All six asynchronous file/batch/directory overloads retain exceptional completion and allow explicit caller recovery through normal future methods. Rejected submissions become failed futures. Counters settle when the actual work completes, independently of cancelling the returned consumer; cancellation does not interrupt underlying filesystem I/O. Failed reads are logged as failed rather than loaded. Counters describe loader I/O, not downstream parsing or scene readiness.

`LoaderReliabilityTest` runs 15 bounded isolated JVM scenarios through the real loader/executor, using synthetic files only. The unchanged baseline fails 12 scenarios; three healthy controls pass. The correction passes all 15, including a 10,000-link alias chain, success-only consumer suppression, explicit fallback, all overloads, cancelled-consumer bookkeeping and rejected submission. Isolation lets each fixture shut down its executor without resetting game singletons or poisoning other tests.

A private differential probe inventoried 10,215 maps in the current local extracted-data snapshot. For all 9,171 structurally loadable maps, 397,369 entries and 1,810,201,551 returned bytes match the original loader exactly, including null slots, lengths, root indices and virtual-size metadata. The remaining 1,044 maps retain historical DRGN0 references after existing extractor relocations: 512 monster sound maps, 512 monster texture maps, 19 party texture maps and one top-level DRGN0 map. Every missing root in that group matches an actual existing Unpacker relocation/removal discriminator; required reads of those dangling historical maps now fail instead of returning shortened lists. Current battle paths use canonical relocated asset paths. No original data or extractor output was modified or uploaded. This comparison proves the enumerated local layout, not every possible mod archive or a full campaign.

Required scene-load failure handling remains separate work: SMap environment waiting has no failure transition, and RetailSubmap can swallow preparation failures before invoking its completion callback. This loader increment exposes failure accurately; it does not prove gameplay recovery, repair damaged assets, cancel already queued executor work at shutdown, bound the executor queue, or establish physical Steam Deck performance. Original-FMV output recovery and draw/swap latency are separate engine findings.
